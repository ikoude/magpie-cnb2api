# magpie-cnb2api

把你自己 CNB 工作区里的 **cnb2api** 接成 magpie 的一个供应商。

装完之后，magpie 里会多出一个叫 **CNB2API** 的提供商，所有 agent 都能直接用，
和官方供应商没有区别。

> **版本 0.1.0 · 早期版本**
>
> 当前为 `0.x`，接口和配置项仍可能调整，升级时请留意 README 的变更。
> 日常使用已经稳定（地址跟随、自动拉起、额度显示、多账号均已验证），
> 但还不宜作为长期依赖。生产环境用之前建议先自行验证一遍。

---

## 它解决什么

cnb2api 跑在 CNB 工作区里，有两个天然毛病：

| 毛病 | 表现 | 插件怎么做 |
|---|---|---|
| **地址会漂移** | 工作区每次重启，`<随机串>-9001.cnb.run` 就换一个 | 后台盯着，地址一变就自动跟上 |
| **工作区会停** | 平台会回收，停了就完全没响应 | 定时检查，停了就调 API 拉起来 |

另外还做了两件事：把工作区名下的**真实额度**（AI credits、核时）显示到 magpie
的用量面板；支持**同时登录多个 CNB 账号**（每个组织/仓库各一个账号）。

---

## 安装

```bash
magpie plugin add /path/to/magpie-cnb2api
```

也支持从本地目录就地加载（不复制文件，改代码直接生效）。
装完在 magpie 的 **Plugins** 列表里能看到 **CNB2API**。

## 配置

两种方式，选一种。

### 方式 A：命令行

```bash
magpie plugin options magpie-cnb2api '{
  "token": "你的 CNB 访问令牌",
  "proxyKey": "sk-你的PROXY_KEY"
}'
```

也可以在 magpie 界面 → Plugins → CNB2API → Options 里填。

### 方式 B：登录表单

```bash
magpie plugin login cnb2api
```

**组织和仓库都是下拉选择**，不用手打：

```
① CNB 访问令牌（CNB → 头像 → 访问令牌）        ← 手填
② 选择组织（共 3 个，每个组织是一个独立账号）
     acme │ bob │ alice                       ← 下拉
③ 确认仓库（acme 下有 2 个在跑 cnb2api）
     acme/my-gateway (运行中) │ acme/other-api (已停止) │ 手动填写仓库名…
④ PROXY_KEY（这个仓库 .cnb.yml 里 env 的值）    ← 手填，不可能自动拿到
⑤ 还要添加其他组织吗？
     就这些，完成登录（只加这 1 个） │ 再添加 bob │ 再添加 alice
```

**PROXY_KEY 跟着仓库走**：它写在该仓库的 `.cnb.yml` 里，属于那个仓库的工作区，
两个仓库完全可以一个 `sk-a`、一个 `sk-b`。所以顺序是
「组织 → 仓库 → 这个仓库的密钥」，最后才问「还要加吗」。

再从 ⑤ 加一个组织时，第 2 个仓库起不必重新粘贴：先问

```
ukelaode/my-gateway 的 PROXY_KEY（每个仓库各有一份）
  和上一个仓库相同 │ 填一个不同的
```

选「相同」就沿用上一个仓库的值（多数人是把同一份 `.cnb.yml` 复制过去的），
选「不同」才弹输入框。加几个组织都不会把 A 仓库的 key 套到 B 仓库上。

只加一个组织也走同一条路——③ 选完仓库、④ 填完密钥，⑤ 直接点
「就这些，完成登录（只加这 1 个）」，剩下的组织以后再登一次就行。

几条不省的规矩：

- **仓库一定让你选**，哪怕只有一个候选也列出来确认 —— 自动挑错了，
  地址和账号会挂到别的仓库上，而且很难发现；候选里没有就走「手动填写仓库名…」
- 一个仓库都没查到 → 要求手填仓库名，组织用上面选的；留空会直接报错
- 只有 **1 个组织** 时（令牌只属于一个组织），选完就直接进仓库那步，
  不会再问「还要加吗」

## 两类凭据，别填混

这是最容易搞错的地方：

| 凭据 | 长什么样 | 干什么用 | 从哪拿 |
|---|---|---|---|
| **CNB 访问令牌** | 一串字母数字，**不是** `sk-` 开头 | 调 CNB OpenAPI：列工作区、读日志、拉起工作区 | CNB → 头像 → 访问令牌 |
| **PROXY_KEY** | 通常 `sk-` 开头 | 调**那个仓库**工作区里的 cnb2api 网关（每个仓库一份） | 那个仓库 `.cnb.yml` 里 `env` 的 `PROXY_KEY` |

> **PROXY_KEY 是仓库级的，不是全局的。** 它属于某个具体仓库的工作区，
> 不同仓库可以不一样；同一个仓库的所有账号（不同人用同一份 `.cnb.yml`）
> 才共用同一个值。所以插件按仓库分别保存、分别取用。

填反了会有明确提示：

```
这看起来是 PROXY_KEY（sk- 开头），不是 CNB 访问令牌。
```

## token 权限

创建令牌时按需勾选。**权限决定能用哪些功能**，勾得越全功能越完整。

### 必需（不勾就没法用）

| Scope | 用途 | 缺少的后果 |
|---|---|---|
| `repo-cnb-trigger:r` | 读流水线启动日志，从中提取工作区地址 | **插件完全不可用**——拿不到地址 |
| `account-engage:r` | 列出令牌属主自己的工作区 | **插件完全不可用**——找不到工作区 |

### 强烈建议（不勾会失去核心能力）

| Scope | 用途 | 缺少的后果 |
|---|---|---|
| `repo-cnb-trigger:rw` | 调 API 启动已停止的工作区 | 地址仍能跟随，但工作区停了**不会自动拉起**，得去网页手动点启动 |

这两项决定了插件的存在意义。`rw` 已包含 `r` 的能力，所以**实际只需勾
`repo-cnb-trigger:rw` 和 `account-engage:r` 两项即可开工**。

### 按功能选配

想要哪个功能就勾哪项，不勾只是对应功能不出现，不影响其他部分。

| Scope | 开启的功能 | 缺少的后果 |
|---|---|---|
| `group-resource:r` | 用量面板显示 AI credits / 核时 | 面板里不显示额度数字 |
| `repo-cnb-detail:r` | 取地址时先查工作区详情（更快） | 回退到读日志，慢一点，无功能损失 |
| `repo-cnb-history:r` | 按模型统计 token 与 credit | 无影响，仅少一份明细 |

### 用不到（不用勾）

| Scope | 为什么不需要 |
|---|---|
| `repo-code:r` | 插件不读你的仓库代码 |

### 快速对照

| 你的需求 | 勾这些 |
|---|---|
| 最小可用 | `repo-cnb-trigger:rw`、`account-engage:r` |
| 要看额度 | 上面 + `group-resource:r` |
| 全都要 | 上面 + `repo-cnb-detail:r`、`repo-cnb-history:r` |

> 权限不够时插件不会沉默。日志和 `magpie quota` 里会写明缺哪一项、影响什么、
> 以及去哪里补。

## 账号与组织

四类信息的**粒度不同**，这是理解的起点：

| 信息 | 粒度 | 说明 |
|---|---|---|
| 账号区分 | 用户 \| 组织/仓库 | 同组织下两个仓库算两个账号 |
| 额度 | 用户 \| 组织 | AI credits 和核时按组织计，不细分到仓库 |
| 工作区地址 | 用户 \| 组织/仓库 | 每个仓库有自己的工作区，地址各自独立 |
| PROXY_KEY | 组织/仓库（仓库级） | 写在该仓库 `.cnb.yml` 的 `env` 里，别的仓库可以不同 |

所以插件把身份定义为 **(用户, 组织/仓库)**：
不同组织额度不同；同组织不同仓库额度相同、但地址不同。

账号在界面、日志、工具输出里的名字统一是 **`用户 | 组织/仓库`**：

```
alice | acme/gateway
```

竖线分隔「用户」和「组织」，组织与仓库之间用 `/`（CNB 自己的写法 `org/repo`）。
不用 `alice@acme/gateway` 这种写法：`组织/仓库` 里本来就有 `/`，再加一个 `@`
看起来像邮箱，读起来分不清哪边是用户、哪边是组织。

> **PROXY_KEY 不参与身份判定。** 它是 api 类型的 apiKey，而且常常几个人
> 用的是同一个 `sk-xxx`（同一份 `.cnb.yml`）。一旦拿它当身份，不管组织和
> 仓库怎么选，所有登录都会被认成同一个账号，列表里永远只有一条。
> 插件只认 CNB 令牌读出的用户 + 所选的组织/仓库；key 单独按仓库存在
> 账号的 metadata 里，只用来发给 cnb2api，不用来区分账号。

### 四种常见情形

**① 多个独立账号，各看各的组织**

```
alice | acme/gateway    ← alice 的令牌，acme 组织的额度
bob   | beta/proxy      ← bob 的令牌，beta 组织的额度
```

两个账号的额度、地址、巡检完全独立。两者指向不同仓库，PROXY_KEY 也各按
自己那个仓库的 `.cnb.yml` 取（只是恰好可能填成同一个值）。

**② 主账号 + 团队成员账号**

bob 被加进 acme 并把令牌也给了你——两个账号看到的是 acme 的同一份额度，
但工作区归属各自的令牌：

```
alice | acme/gateway    ← 用 alice 的令牌
bob   | acme/gateway    ← 用 bob 的令牌
```

想用哪个账号就在 magpie 里切哪个。**不要指望一个账号同时用两个组织的额度**
——CNB 不支持这种"合并"。

**③ 一个主账号，名下多个组织（最常见）**

alice 同时是 acme、gamma 的成员，每个组织各有独立额度和工作区：

```
alice | acme/gateway    → 额度 1166，地址 7mzc****-9001.cnb.run
alice | gamma/gateway   → 额度 500， 地址 xmjq****-9001.cnb.run
```

**④ 同组织下多个仓库**

alice 在 acme 下有两个都跑着 cnb2api 的仓库：

```
alice | acme/gateway-a  → 额度 1166（共享），地址 7mzc****-9001.cnb.run
alice | acme/gateway-b  → 额度 1166（共享），地址 ab12****-9001.cnb.run
```

额度是同一个（都属 acme），但地址和巡检完全独立——这样才能分别拉起。

③ 和 ④ 有两种加法，结果完全一样，随便挑：

| 加法 | 怎么做 | 适合 |
|---|---|---|
| **一次加多个** | 一次登录里连着加，每选完一个组织会问「还要添加其他组织吗」，点「再添加 xxx」继续，加完点「就这些，完成登录」 | 令牌只贴一次，最省事 |
| **一次加一个** | 每次登录只选一个组织，最后点「就这些，完成登录」，下次再跑一遍 `login` | 想一个一个核对，或先加一个用着 |

一次加多个只是为了**少贴几次令牌**，不是必须的。分几次登录时每份令牌
各贴一次，账号身份由「用户 + 组织/仓库」决定，跟是不是同一次登录无关；
同一个组合重复登录只会覆盖原来那条，不会越登越多。

### 怎么登录

**令牌只需要填一次。** 同一个令牌下的多个组织可以在一次登录里连着加：

```bash
magpie plugin login cnb2api
#   令牌          粘贴一次
#   选择组织      点 ikoude
#   确认仓库      ikoude/cnb2api
#   PROXY_KEY     粘贴一次（ikoude/cnb2api 这个仓库的）
#   还要添加其他组织吗？ → 再添加 ukelaode
#   确认仓库      ukelaode/cnb2api
#   PROXY_KEY     → 和上一个仓库相同 / 填一个不同的
#   还要添加其他组织吗？ → 再添加 qdirs
#   确认仓库      qdirs/cnb2api
#   PROXY_KEY     → 和上一个仓库相同 / 填一个不同的
#   还要添加其他组织吗？ → 就这些，完成登录
```

一次登录就把三个组织全加好了。中间每一步都能选「就这些，完成登录」提前收工，
所以只想要其中两个的话，加完第二个就停。

**PROXY_KEY 是每个仓库一份**，所以加第二个仓库时会先问你「和上一个仓库相同 /
填一个不同的」——同一份 `.cnb.yml` 复制到几个仓库很常见，选「相同」就不用再贴。
选「不同」才弹输入框。**不会把一个仓库的 key 套到另一个仓库上。**

**只加一个也完全 OK。** 选完组织、仓库、填完 PROXY_KEY，最后那一步会写成
「就这些，完成登录（只加这 1 个）」，点它登录结束——
剩下的组织想加的时候再跑一次 `magpie plugin login cnb2api` 就行。
那次会把令牌和 PROXY_KEY 再贴一遍，这是唯一的代价，账号本身没有区别。

换账号（另一个人的令牌）才需要重新跑一次 `login`：

```bash
magpie plugin login cnb2api     # bob 的令牌 → 选 acme → 选 acme/gateway
```

组织和仓库都是下拉选择，选项来自令牌实际可访问的列表。

> **仓库必须由你选，插件不会替你挑。** 地址是按仓库算的，不指定就不知道该
> 跟哪个工作区。候选列表是**筛出来的**（该组织下有工作区、且启动日志里出现过
> `PROXY_URI=`，名字带 `cnb2api` 的直接收录），所以：
>
> - 有候选 → 全列出来给你选，**只有一个也要你点**（选项里标「运行中 / 已停止」）
> - 候选里没有你要的 → 列表最后一条永远是 **「手动填写仓库名…」**，选它再手打
>   （日志滚掉了、仓库刚建、工作区是别人的，都会导致漏筛）
> - 一个都没筛到 → 直接要求手填，不填就失败
>
> 没选仓库登录会直接失败，不会替你猜。
>
> 选定的组织/仓库会写进账号身份，所以**同一份令牌加几个组织就是几个账号**。
> 想换某个账号的组织或仓库，重新登录一次即可，同组合会替换原来那条。

### PROXY_KEY 不会被自动填，而且一个仓库一份

登录一定会问 **PROXY_KEY**（位置在 ③ 组织/仓库确认之后、⑤「还要加吗」之前），
必须手打。插件没有任何办法自动拿到它：

- 它只是**那个仓库** `.cnb.yml` 里 `env` 的一个值，CNB 的 OpenAPI 读不到工作区
  环境变量（读得到就等于谁拿到令牌都能读别人的密钥）
- 想自动读就得给令牌加 `repo-code:r`（读仓库文件）去解析 `.cnb.yml`，
  而那里还可能是 `${SECRET}` 之类的引用，解析出来也不是真值。为了少打一次
  字符串去开"能读代码"的权限，不划算

粒度是**仓库**，不是账号也不是网关：

| 情况 | key 一样吗 |
|---|---|
| 同一个仓库、不同人的令牌 | 一样（同一份 `.cnb.yml`） |
| 同一个人的两个仓库 | **可以不一样**（各自 `.cnb.yml` 的 env） |
| 同一个组织下两个仓库 | **可以不一样** |

所以多仓库登录时插件按仓库分别问、分别存：第 2 个仓库起先问
「和上一个仓库相同 / 填一个不同的」，选相同就沿用，选不同才弹输入框。
填缺了哪个仓库，`authorize` 会点名报错
（`这些仓库还没填 PROXY_KEY：acme/gateway-b`），不会存一条 key 为空的账号。

## 仓库可以不叫 cnb2api

登录选仓库时，候选列表**不靠名字判断**，只看启动日志里有没有 `PROXY_URI=`：

```
alice/blog           日志: "listening on 3000"            → 不出现在候选里
alice/demo           日志: "demo running"                  → 不出现在候选里
acme/my-ai-gateway   日志: "PROXY_URI=https://ab12-..."    → 候选之一
```

所以仓库可以叫任何名字，也可以放在任何组织下——只要它真的跑着 cnb2api。

登录时会先合并三处来源得到组织列表，再筛出该组织下跑着 cnb2api 的仓库，
**列出来给你选**（不是替你选）。筛的意思是"过滤候选"，不是"帮你看哪个对"：
同一个组织下如果有两个仓库都跑着 cnb2api，两个都会列出来，你自己决定用哪个。
筛漏了就走列表末尾的「手动填写仓库名…」。

## 用量与额度显示

```
CNB2API · running
  ikoude | ikoude/cnb2api   workspace     ok · 860l****-9001.cnb.run         (aside)
                            AI credits    ▓▓▓▓▓▓▓░░░  801.1 / 1166 cr   天才程序员专属特权 +666 · 冻结 0 · 可用 364.9
  qdirs  | qdirs/cnb2api    workspace     ok · o0iw****-9001.cnb.run         (aside)
                            AI credits    ░░░░░░░░░░  0 / 1166 cr       天才程序员专属特权 +666 · 冻结 96.2 · 可用 1069.8
```

第一列就是账号名 `用户 | 组织/仓库`。多个组织、多个仓库时，
光看用户名或光看组织都分不清是哪一条，带上仓库才唯一。

### workspace 那一行

显示的是 **API 端点**，也就是"账号现在能不能用"的直接证据。默认打码，
因为额度面板常被截图分享：

```
ok · 860l****-9001.cnb.run      ← 前 4 位认得出是哪个 + 端口域名看得出正常
```

要看完整地址：

```bash
CNB2API_SHOW_FULL_HOST=1 magpie
```

打码只影响显示，实际请求用的永远是完整地址。

### 额度的含义

| 显示项 | 含义 |
|---|---|
| `801.1 / 1166 cr` | 已用 / 总额（额度单位是 credit，1 credit ≈ 0.001 元） |
| `冻结 96.2` | 已预扣但还在计费周期内、尚未结算的部分 |
| `可用 1069.8` | 现在还能用多少 = 总额 − 已用 − 冻结 |
| `天才程序员专属特权 +666` | 额外赠送的额度，已计入总额 |
| `+1024 已过期` | 赠送额度已失效，但仍占着总额的位置 |

### 数据显示规则

所有账号的排版骨架完全一致，都是 `进度条 + 特权 · 冻结 · 可用`：

- 进度条显示已用比例和 `已用/总额 单位`
- 冻结为 0 时也照常显示 `冻结 0`，不省略
- 整数不拖 `.0`（写 `0` 而不是 `0.0`）
- 文字里不重复 `已用/总额`，只补充进度条表达不了的信息

## 工具

插件注册了三个工具，agent 可以直接调用：

| 工具 | 作用 |
|---|---|
| `cnb2api_workspace_status` | 查状态、仓库、地址、工作区编号 |
| `cnb2api_workspace_start` | 拉起工作区（已停止时） |
| `cnb2api_quota` | 查核时 / AI Credits 余量 |

### 工作区不会被插件停掉

插件**不做空闲自动停止**，也不提供停止工具。工作区被停掉后重启要
30–90 秒，而且地址会变——为了省核时把正在用的工作区停掉，代价是
下一次请求先卡一分多钟。需要停的时候直接在 CNB 网页上停。

想随时了解还剩多少核时，用 `cnb2api_quota` 或看 magpie 的用量面板。

## 选项

全部可选。不填就用默认值或从登录信息里取。

> 改完选项需要重启 magpie 才生效——选项在插件加载时读入。

| 选项 | 默认 | 说明 |
|---|---|---|
| `token` | — | CNB 访问令牌。**建议用登录表单填** |
| `proxyKey` | — | `.cnb.yml` 里那个 PROXY_KEY |
| `repo` | — | **建议用登录表单选**。地址按仓库算，必须指定 |
| `models` | `deepseek-v4.1-flash` | 逗号分隔 |
| `branch` | `main` | 拉起工作区时用的分支 |
| `checkSeconds` | `120` | 巡检间隔（秒） |
| `autoStart` | `true` | 工作区停了是否自动拉起 |
| `port` | `9001` | cnb2api 监听的端口 |

`repo` 接受多种写法：

```
https://cnb.cool/alice/my-gateway
https://cnb.cool/alice/my-gateway/-/tree/main
git@cnb.cool:alice/my-gateway.git
alice/my-gateway
my-gateway                    ← 只写名字，组织自动补
```

## 安全

插件代码里**不含任何凭据**，`DEFAULTS.token` 是空字符串。

| 层 | 隔离方式 |
|---|---|
| 插件代码 | 无硬编码，无默认值 |
| 配置 | 每人机器上独立，`plugins.json` 权限 `600` |
| 账号状态 | 按 token 指纹分上下文，异步调用链隔离 |
| 缓存键 | 用 token 指纹，不存明文 |
| CNB 侧 | `account-engage:r` 只列**令牌属主自己**的工作区 |

### 多账号为什么不会串

插件函数只被调用一次，所有账号共用同一份闭包。若用普通变量记录"当前账号"，
两个账号并发请求时就会互相干扰——A 的 token 可能被带进 B 的请求。
插件用 `AsyncLocalStorage` 把账号上下文绑定在异步调用链上，天然隔离。

---

## 什么时候刷新

- **登录后**：立刻触发一轮，不用等
- **定时**：每 `checkSeconds` 秒（默认 120）
- **请求失败时**：自动重新识别地址并重试一次
- **凭据变更时**：立刻重置该账号状态并重新识别

凭据变更时会清掉之前的错误状态，所以换了新 token 不需要重启 magpie。

## 调试

```bash
magpie logs              # 看插件日志（带账号前缀）
magpie quota             # 看当前额度
```

日志里的账号前缀让你分清是谁：

```
[ikoude | ikoude/cnb2api] 已就绪：https://860lo2zlkf-9001.cnb.run
[qdirs | qdirs/cnb2api]   已就绪：https://o0iwd9t7ek-9001.cnb.run
```

常见现象：

| 现象 | 原因 | 处理 |
|---|---|---|
| `401`（CNB OpenAPI 那侧） | 令牌无效或过期 | CNB → 头像 → 访问令牌，重新生成 |
| `401`（请求 cnb2api 时）| 这个账号的 PROXY_KEY 和它那个仓库 `.cnb.yml` 的 `PROXY_KEY` 不一致 | 重新登录这个账号，按那个仓库的值填 |
| 提示"缺少必需权限" | 令牌没勾 scope | 编辑令牌勾上后重启工作区 |
| 仓库不存在 | `repo` 填错，或令牌无权访问 | 核对组织/仓库是否正确 |
| 地址是 placeholder | 还没取到地址 | 等 30–90 秒（工作区冷启动） |
| 额度面板没有数字 | 缺 `group-resource:r` | 补勾后重试 |

## 已知限制

- 两个账号指向**同一个仓库**时会共用同一个工作区，地址和额度是同一份。
  这是 CNB 侧的模型决定的，插件无法绕过。
- PROXY_KEY 按仓库存：同一个账号换了仓库就等于换了 key，要重新登录一次
  （插件不会把旧仓库的 key 带过去）。
- 凭据存在 magpie 的配置文件里。如果机器多人共用，注意文件权限。
- 工作区冷启动要 30–90 秒，首次请求会等；之后有缓存。
