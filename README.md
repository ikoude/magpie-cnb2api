# magpie-cnb2api

把你自己 CNB 工作区里的 **cnb2api** 接成 magpie 的一个供应商。

装完之后，magpie 里会多出一个叫 **CNB2API** 的提供商，所有 agent 都能直接用，
和官方供应商没有区别。

> 本文里的组织名、用户名、仓库名、额度和地址**全部是示例**（`alice`、`acme`、
> `acme/gateway` 这类），不是任何人的真实数据。

---

## 它解决什么

cnb2api 跑在 CNB 工作区里，有两个天然毛病：

| 毛病 | 表现 | 插件怎么做 |
|---|---|---|
| **地址会漂移** | 工作区每次重启，`<随机串>-<端口>.cnb.run` 就换一个 | 后台盯着，地址一变就自动跟上 |
| **工作区会停** | 平台会回收，停了就完全没响应 | 定时检查，停了就调 API 拉起来 |

另外还做两件事：把工作区名下的**真实额度**（AI credits、核时）显示到 magpie
的用量面板；支持**同时登录多个 CNB 账号**（每个「用户 + 组织/仓库」各一个账号）。

拉起工作区之前会先看一眼额度：credits 已经用尽就**不拉**（拉起来也只会回 402，
白烧核时），额度补足后自动补上。

---

## 安装

```bash
magpie plugin add /path/to/magpie-cnb2api
```

也支持从本地目录就地加载（不复制文件，改代码直接生效）。
装完在 magpie 的 **Plugins** 列表里能看到 **CNB2API**。

## 概念：四类信息，粒度不一样

这是理解后面所有行为的前提。

| 信息 | 粒度 | 说明 |
|---|---|---|
| 账号区分 | 用户 + 组织/仓库 | 同组织下两个仓库算两个账号 |
| 额度 | 用户 + 组织 | AI credits 和核时按组织计，不细分到仓库 |
| 工作区地址 | 用户 + 组织/仓库 | 每个仓库有自己的工作区，地址各自独立 |
| PROXY_KEY | 组织/仓库 | 写在该仓库 `.cnb.yml` 的 `env` 里，别的仓库可以不同 |

所以账号身份是 **(用户, 组织/仓库)**：不同组织额度不同；同组织不同仓库
额度相同、但地址不同。

账号在界面、日志、工具输出里的名字统一写成 **`用户 | 组织/仓库`**：

```
alice | acme/gateway
```

竖线分隔「用户」和「组织」，组织与仓库之间用 `/`（CNB 自己的写法 `org/repo`）。
不用 `alice@acme/gateway` 那种写法：`组织/仓库` 里本来就有 `/`，再加一个 `@`
看起来像邮箱，读起来分不清哪边是用户、哪边是组织。

> **PROXY_KEY 不参与身份判定。** 它是 api 类型的 apiKey，而同一份 `.cnb.yml`
> 常常被几个人用（key 恰好相同）。一旦拿它当身份，不管组织和仓库怎么选，
> 所有登录都会被认成同一个账号，列表里永远只有一条。
> 插件只认 CNB 令牌读出的用户 + 所选的组织/仓库；key 按仓库单独存在账号的
> metadata 里，只用来发给 cnb2api。

### 四种常见情形

**① 多个独立账号，各看各的组织**

```
alice | acme/gateway    ← alice 的令牌，acme 的额度
bob   | beta/proxy      ← bob 的令牌，beta 的额度
```

额度、地址、巡检完全独立。

**② 主账号 + 团队成员账号**

bob 被加进 acme，令牌也交给了你。两个账号看到的是 acme 的同一份额度，
但工作区归属各自的令牌：

```
alice | acme/gateway    ← 用 alice 的令牌
bob   | acme/gateway    ← 用 bob 的令牌
```

想用哪个就在 magpie 里切哪个。**不要指望一个账号同时用两个组织的额度**
——CNB 不支持这种"合并"。

**③ 一个主账号，名下多个组织（最常见）**

alice 同时是 acme、gamma 的成员，每个组织有各自的额度和工作区：

```
alice | acme/gateway    → 额度按 acme 算，地址 <a>-<port>.cnb.run
alice | gamma/gateway   → 额度按 gamma 算，地址 <b>-<port>.cnb.run
```

**④ 同组织下多个仓库**

alice 在 acme 下有两个都跑着 cnb2api 的仓库：

```
alice | acme/gateway-a  → 额度按 acme 算（共享），地址 <a>-<port>.cnb.run
alice | acme/gateway-b  → 额度按 acme 算（共享），地址 <b>-<port>.cnb.run
```

额度是同一份（都属 acme），但地址、巡检、PROXY_KEY 各自独立。

## 登录

两种方式，选一种。

### 方式 A：登录表单（推荐）

```bash
magpie plugin login cnb2api
```

组织和仓库都是**下拉选择**，选项来自令牌实际可访问的列表：

```
① CNB 访问令牌 · 在 CNB 头像 → 访问令牌 里生成          ← 手填
② 选择组织 · 该令牌可访问 N 个组织，每个组织对应一个独立账号
     acme │ beta │ gamma                                ← 下拉
③ 选择仓库 · acme 下有 2 个在跑 cnb2api
     acme/gateway（运行中）│ acme/worker（已停止）│ 手动填写仓库名…
④ PROXY_KEY · 这个仓库 .cnb.yml 里 env 的值              ← 手填，不可能自动拿到
⑤ 还要添加其他组织吗
     完成登录 · 只加这 1 个 │ 再加一个组织：beta │ 再加一个组织：gamma
```

**顺序是 组织 → 仓库 → 这个仓库的密钥 → 还要加吗。** PROXY_KEY 跟着仓库
走，所以仓库一确定就问它；最后一步只管"要不要继续加"，答完登录立刻结束。

从 ⑤ 再加一个组织时，第二个仓库起不必重新粘贴：

```
beta/gateway 的 PROXY_KEY · 每个仓库各有一份
  和上一个仓库相同  — 沿用 acme/gateway 的值
  填一个不同的      — 这个仓库 .cnb.yml 里是另一个值
```

选「相同」沿用上一个仓库的值（同一份 `.cnb.yml` 复制到几个仓库很常见），
选「不同」才弹输入框。**不会把一个仓库的 key 套到另一个仓库上。**

**只加一个也完全 OK。** ③ 选完仓库、④ 填完密钥，⑤ 点
「完成登录 · 只加这 1 个」就结束。剩下的组织想加的时候再跑一次
`magpie plugin login cnb2api` —— 那次要重新贴令牌和 PROXY_KEY，这是唯一的代价，
账号本身没有区别。

想一次加多个，只是想**少贴几次令牌**，不是必须的。

### 方式 B：命令行选项

```bash
magpie plugin options magpie-cnb2api '{
  "token": "你的 CNB 访问令牌",
  "proxyKey": "sk-你的PROXY_KEY",
  "repo": "acme/gateway"
}'
```

也可以在 magpie 界面 → Plugins → CNB2API → Options 里填。
这种方式只能配**一个**账号（组织/仓库由 `repo` 决定），多账号请用方式 A。

### 仓库一定要你选

地址按仓库算，不指定就不知道该跟哪个工作区。候选列表是**筛出来的**
（该组织下有工作区、且启动日志里出现过 `PROXY_URI=`，名字带 `cnb2api`
的直接收录），但这只是过滤候选，不是替你决定：

- 有候选 → 全列出来给你选，**只有一个也要你点**（选项标「运行中 / 已停止」）
- 候选里没有 → 列表最后一条永远是 **「手动填写仓库名…」**，选它再手打
  （日志滚掉了、仓库刚建、工作区是别人的，都会导致漏筛）
- 一个都没筛到 → 直接要求手填，不填就失败

没选仓库登录会直接失败，不会替你猜。**自动挑错仓库的后果是静默的**：
地址、账号、巡检全挂到另一个仓库上，很难发现，所以这里不做任何猜测。

> 候选**不看名字**，只看日志里有没有 `PROXY_URI=`。所以仓库可以叫任何名字，
> 放在任何组织下——只要它真的跑着 cnb2api。
>
> ```
> alice/blog           日志: "listening on 3000"          → 不进候选
> acme/my-ai-gateway   日志: "PROXY_URI=https://…"        → 进候选
> ```

### 选定的组织/仓库会写进账号身份

所以**同一份令牌加几个组织就是几个账号**。想换某个账号的组织或仓库，
重新登录一次即可——同一个「用户 + 组织/仓库」会替换原来那条，不会越加越多。

## 两类凭据，别填混

这是最容易搞错的地方：

| 凭据 | 长什么样 | 干什么用 | 从哪拿 |
|---|---|---|---|
| **CNB 访问令牌** | 一串字母数字，**不是** `sk-` 开头 | 调 CNB OpenAPI：列工作区、读日志、拉起工作区 | CNB → 头像 → 访问令牌 |
| **PROXY_KEY** | 通常 `sk-` 开头 | 调**那个仓库**工作区里的 cnb2api 网关 | 那个仓库 `.cnb.yml` 里 `env` 的 `PROXY_KEY` |

填反了会有明确提示：

```
这看起来是 PROXY_KEY（sk- 开头），不是 CNB 访问令牌。
```

### PROXY_KEY 为什么不能自动填

插件没有任何办法自动拿到它：

- 它只是**那个仓库** `.cnb.yml` 里 `env` 的一个值。CNB 的 OpenAPI 读不到
  工作区环境变量（读得到就等于谁拿到令牌都能读别人的密钥）
- 想自动读就得给令牌加 `repo-code:r`（读仓库文件）去解析 `.cnb.yml`，
  而那里还可能是 `${SECRET}` 一类的引用，解析出来也不是真值。为省一次粘贴
  去开"能读代码"的权限，不划算

它的粒度是**仓库**，不是账号、也不是网关：

| 情况 | key 一样吗 |
|---|---|
| 同一个仓库、不同人的令牌 | 一样（同一份 `.cnb.yml`） |
| 同一个人的两个仓库 | **可以不一样** |
| 同一个组织下两个仓库 | **可以不一样** |

所以多仓库登录时按仓库分别问、分别存。填缺了哪个仓库，`authorize` 会点名
报错（`还没填这些仓库的 PROXY_KEY · acme/worker`），不会存一条 key 为空的账号。

## token 权限

创建令牌时按需勾选。**权限决定能用哪些功能**，勾得越全功能越完整。

### 必需（不勾就没法用）

| Scope | 用途 | 缺少的后果 |
|---|---|---|
| `repo-cnb-trigger:r` | 读流水线启动日志，从中提取工作区地址 | **插件完全不可用**——拿不到地址 |
| `account-engage:r` | 列出令牌属主自己的工作区 | **插件完全不可用**——找不到工作区 |

### 强烈建议

| Scope | 用途 | 缺少的后果 |
|---|---|---|
| `repo-cnb-trigger:rw` | 调 API 启动已停止的工作区 | 地址仍能跟随，但工作区停了**不会自动拉起**，得去网页手动点启动 |

`rw` 已包含 `r` 的能力，所以**实际只需勾 `repo-cnb-trigger:rw` 和
`account-engage:r` 两项即可开工**。

### 按功能选配

| Scope | 开启的功能 | 缺少的后果 |
|---|---|---|
| `group-resource:r` | 用量面板显示 AI credits / 核时 | 面板里不显示额度数字 |
| `repo-cnb-detail:r` | 取地址时先查工作区详情（更快） | 回退到读日志，慢一点，无功能损失 |
| `repo-cnb-history:r` | 按模型统计 token 与 credit | 无影响，仅少一份明细 |

### 用不到

| Scope | 为什么不需要 |
|---|---|
| `repo-code:r` | 插件不读你的仓库代码 |

### 快速对照

| 你的需求 | 勾这些 |
|---|---|
| 最小可用 | `repo-cnb-trigger:rw`、`account-engage:r` |
| 要看额度 | 上面 + `group-resource:r` |
| 全都要 | 上面 + `repo-cnb-detail:r`、`repo-cnb-history:r` |

> 权限不够时插件不会沉默。日志和 `magpie quota` 里会写明缺哪一项、影响什么、
> 以及去哪里补。

## 用量与额度显示

```
CNB2API · running
  alice | acme/gateway    workspace     ok · 1a2b****-9001.cnb.run          (aside)
                          AI credits    ▓▓▓▓▓▓▓░░░  800 / 1200 cr        赠送额度 +600 · 冻结 0 · 可用 400
  alice | gamma/gateway   workspace     ok · 3c4d****-9001.cnb.run          (aside)
                          AI credits    ░░░░░░░░░░  0 / 1200 cr           赠送额度 +600 · 冻结 100 · 可用 1100
```

第一列就是账号名 `用户 | 组织/仓库`。多个组织、多个仓库时，光看用户名或
光看组织都分不清是哪一条，带上仓库才唯一。

### workspace 那一行

显示的是 **API 端点**，也就是"账号现在能不能用"的直接证据。默认打码，
因为额度面板常被截图分享：

```
ok · 1a2b****-9001.cnb.run      ← 前 4 位认得是哪个 + 端口域名看得出正常
```

要看完整地址：

```bash
CNB2API_SHOW_FULL_HOST=1 magpie
```

打码只影响显示，实际请求用的永远是完整地址。

### 额度的含义

| 显示项 | 含义 |
|---|---|
| `800 / 1200 cr` | 已用 / 总额（单位是 credit，1 credit ≈ 0.001 元） |
| `冻结 100` | 已预扣但还在计费周期内、尚未结算的部分 |
| `可用 1100` | 现在还能用多少 = 总额 − 已用 − 冻结 |
| `赠送额度 +600` | 额外赠送的部分，已计入总额（具体名目由 CNB 给出） |
| `+1024 已过期` | 赠送额度已失效，但仍占着总额的位置 |

### 数据显示规则

所有账号排版骨架一致，都是 `进度条 + 赠送 · 冻结 · 可用`：

- 进度条显示已用比例和 `已用/总额 单位`
- 冻结为 0 时也照常显示 `冻结 0`，不省略
- 整数不拖 `.0`（写 `0` 而不是 `0.0`）
- 文字里不重复 `已用/总额`，只补充进度条表达不了的信息

## 额度用尽时不会拉起工作区

工作区停着、又轮到要拉起时，插件先看一次所属组织的 AI credits，用尽就不拉：

```
AI credits 已用尽（已用 1200 / 1200 cr）· 没有拉起工作区，额度恢复后会自动再试
```

道理很直接：cnb2api 是 AI 网关，credits 用尽后它对每个请求都回

```
402 [EXCEEDING_LIMIT]AI 积分已用尽，请联系根组织管理员提升配额
```

这时候把工作区拉起来，只是先烧掉 30–90 秒冷启动和核时，最后仍然只拿到 402。
所以：

- **不提交** `/workspace/start`，日志只留一句原因（同一个结论不会反复刷）
- 请求立刻失败并说明原因，不会再傻等 90 秒去拿一个不会出现的地址
- 巡检照常每 `checkSeconds` 秒看一眼额度，**额度补足后自动拉起**，不用手动干预

三种边界情况：

| 情况 | 行为 |
|---|---|
| 额度查不到（缺 `group-resource:r`、接口临时抽风） | **照常拉起** —— 拦住一个本来能用的工作区，比放过一个注定 402 的更糟 |
| 余额很少但还有 | 照常拉起，不做"快不够了先别用"的判断 |
| 工作区已经在跑 | 与拉起无关；请求真被 402 拒绝时，会补一句"额度用尽期间不会自动拉起" |

额度**按组织**算（和用量面板口径一致），同一组织下多个仓库共用这一份。

## 工具

插件注册了三个工具，agent 可以直接调用：

| 工具 | 作用 |
|---|---|
| `cnb2api_workspace_status` | 查状态、仓库、地址、工作区编号 |
| `cnb2api_workspace_start` | 拉起工作区（已停止时；额度用尽会拒绝并说明原因） |
| `cnb2api_quota` | 查核时 / AI Credits 余量 |

### 工作区不会被插件停掉

插件**不做空闲自动停止**，也不提供停止工具。工作区停掉后重启要 30–90 秒，
而且地址会变——为了省核时把正在用的工作区停掉，代价是下一次请求先卡一分多钟。
需要停的时候直接在 CNB 网页上停。

想随时了解还剩多少核时，用 `cnb2api_quota` 或看 magpie 的用量面板。

## 选项

全部可选。不填就用默认值或从登录信息里取。

> 改完选项需要重启 magpie 才生效——选项在插件加载时读入。

| 选项 | 默认 | 说明 |
|---|---|---|
| `token` | — | CNB 访问令牌。**建议用登录表单填** |
| `proxyKey` | — | 那个仓库 `.cnb.yml` 里的 PROXY_KEY |
| `repo` | — | **建议用登录表单选**。地址按仓库算，必须指定 |
| `models` | `deepseek-v4.1-flash` | 逗号分隔 |
| `branch` | `main` | 拉起工作区时用的分支 |
| `checkSeconds` | `120` | 巡检间隔（秒） |
| `autoStart` | `true` | 工作区停了是否自动拉起（AI 额度用尽时不会拉，见上文） |
| `port` | `9001` | cnb2api 监听的端口 |

`repo` 接受多种写法：

```
https://cnb.cool/<组织>/<仓库>
https://cnb.cool/<组织>/<仓库>/-/tree/main
git@cnb.cool:<组织>/<仓库>.git
<组织>/<仓库>
<仓库>                    ← 只写名字，组织用登录时选的那个补
```

## 安全

插件代码里**不含任何凭据**，`DEFAULTS.token` 是空字符串。

| 层 | 隔离方式 |
|---|---|
| 插件代码 | 无硬编码，无默认值 |
| 配置 | 每人机器上独立，`plugins.json` 权限 `600` |
| 账号状态 | 按 token 指纹分上下文，异步调用链隔离 |
| 缓存键 | 用 token 指纹，不存明文 |
| CNB 侧 | `account-engage:r` 只列**令牌属主自己**的工作区 |

### 多账号为什么不会串

插件函数只被调用一次，所有账号共用同一份闭包。若用普通变量记录"当前账号"，
两个账号并发请求时就会互相干扰——A 的 token 可能被带进 B 的请求。
插件用 `AsyncLocalStorage` 把账号上下文绑定在异步调用链上，天然隔离。

## 什么时候刷新

- **登录后**：立刻触发一轮，不用等
- **定时**：每 `checkSeconds` 秒（默认 120）
- **请求失败时**：自动重新识别地址并重试一次
- **凭据变更时**：立刻重置该账号状态并重新识别

凭据变更时会清掉之前的错误状态，所以换了新 token 不需要重启 magpie。

## 调试

```bash
magpie logs              # 看插件日志（带账号前缀）
magpie quota             # 看当前额度
```

日志里的账号前缀让你分清是谁：

```
[alice | acme/gateway]  已就绪 · 1a2b****-9001.cnb.run
[alice | gamma/gateway] 已就绪 · 3c4d****-9001.cnb.run
```

常见现象：

| 现象 | 原因 | 处理 |
|---|---|---|
| `401`（CNB OpenAPI 那侧） | 令牌无效或过期 | CNB → 头像 → 访问令牌，重新生成 |
| `401`（请求 cnb2api 时） | 这个账号的 PROXY_KEY 和它那个仓库 `.cnb.yml` 的不一致 | 重新登录该账号，按那个仓库的值填 |
| `402 [EXCEEDING_LIMIT]` | 所属组织的 AI credits 用尽 | 联系根组织管理员提升配额；期间插件不会自动拉起工作区 |
| 提示"缺少必需权限" | 令牌没勾 scope | 编辑令牌勾上后重启工作区 |
| 仓库不存在 | `repo` 填错，或令牌无权访问 | 核对组织/仓库是否正确 |
| 地址是 placeholder | 还没取到地址 | 等 30–90 秒（工作区冷启动） |
| 额度面板没有数字 | 缺 `group-resource:r` | 补勾后重试 |

## 已知限制

- 两个账号指向**同一个仓库**时会共用同一个工作区，地址和额度是同一份。
  这是 CNB 侧的模型决定的，插件无法绕过。
- PROXY_KEY 按仓库存：换了仓库就等于换了 key，要重新登录一次
  （插件不会把旧仓库的 key 带过去）。
- 凭据存在 magpie 的配置文件里。如果机器多人共用，注意文件权限。
- 工作区冷启动要 30–90 秒，首次请求会等；之后有缓存。
